# MAX бот с Yandex AI Studio RAG (строго по документам)

## 1) Используемые репозитории

### `all-mute/yc-ai-tg-demo`
- Показывает рабочий паттерн: отдельный скрипт создания индекса (`create_rag_index.py`) + чат-бот + хранение ID индекса.
- Важно: в демо используется **Search API Generative answer** и Telegram, что нам не подходит для строгого офлайн-RAG по внутренним документам в MAX.
- Что можно переиспользовать:
  - разделение на bootstrap/индексацию и runtime-бота;
  - хранение конфигурации в `.env`;
  - практика отдельного шага подготовки индекса до запуска бота.

### `nabinabi11/max-yandexgpt`
- Это минимальный Python-фреймворк для бота именно в **MAX messenger**.
- Уже есть:
  - webhook/polling-обвязка сообщений MAX;
  - streaming/non-streaming ответы;
  - конфигурация через env;
  - интеграция с YandexGPT через OpenAI-compatible endpoint.
- Ограничение: в текущем виде это обычный LLM-бот без «жесткого» RAG-контроля источников.

### `yandex-cloud/yandex-ai-studio-sdk`
- Нужный foundation для production-интеграции с AI Studio.
- По README:
  - есть `Search indexes` (создание/обновление/поиск по индексам);
  - есть `Tools`, включая Search Index Tool;
  - Assistants/Threads отмечены как deprecated, поэтому лучше опираться на актуальные API Chat/Completions + Search Index.
- Есть CLI для построения vector-store индексов, но в вашем кейсе индекс уже создаётся и поддерживается в AI Studio UI.

## 2) Целевая архитектура

## Требование
Бот должен отвечать **только на базе извлечённых из индекса документов**, без AI Search интернета.

## Архитектурный контур
1. **MAX Transport Layer**
   - Получение сообщений из MAX;
   - Маршрутизация по пользователю/сессии.

2. **RAG Retrieval Layer (AI Studio Search Index)**
   - Запрос top-k чанков только из заранее заданного `INDEX_ID`;
   - Фильтрация по score/релевантности;
   - Запрет fallback на web/generative search.

3. **Grounded Generation Layer (YandexGPT через AI Studio)**
   - Модель получает:
     - системные guardrails;
     - вопрос пользователя;
     - только отобранные фрагменты документов.
   - Модель обязана:
     - отвечать только по контексту;
     - при нехватке данных возвращать «недостаточно данных в предоставленных документах».

4. **Policy/Validation Layer (критично)**
   - Pre-check: если retrieval пустой/ниже порога -> отказ от ответа по существу.
   - Post-check: запрет «галлюцинаций» через mandatory citations (id документа/чанка).
   - Логирование `question -> retrieved_chunks -> answer` для аудита.

## 3) Ограничения модели извлечёнными данными

Используется **двухконтурный контроль**:

1. **На уровне orchestration (обязательный):**
   - Никогда не отправлять в модель пользовательский запрос без retrieval-контекста.
   - Отключить любые web-инструменты/генеративный поиск.
   - Использовать только `INDEX_ID`, который задан в конфиге.

2. **На уровне system prompt (дополнительный, но не единственный):**
   - Явный запрет на внешние знания;
   - Формат ответа с цитатами источников;
   - Обязательный отказ при нехватке фактов.

### Рекомендуемый system prompt
```text
Ты — консультант для предпринимателей по мерам государственной поддержки бизнеса.
Отвечай строго и только на основании фрагментов CONTEXT.

Правила:
1) Запрещено использовать знания вне CONTEXT.
2) Если в CONTEXT нет достаточной информации, ответь: 
   "Недостаточно данных в предоставленных документах." 
   и уточни, каких данных не хватает.
3) Не выдумывай факты, даты, числа, названия.
4) В конце каждого существенного утверждения указывай ссылку на источник в формате [doc_id:chunk_id].
5) Если источники противоречат друг другу — явно укажи это.
```

## 4) Рекомендуемый стек реализации

- **База для MAX-бота:** взять `max-yandexgpt` как каркас транспорта/обработчиков.
- **RAG API:** использовать `yandex-ai-studio-sdk` для поиска по существующему индексу AI Studio.
- **Конфигурация:**
  - `MAX_TOKEN`
  - `YANDEX_API_KEY`
  - `YANDEX_FOLDER_ID`
  - `YA_RAG_INDEX_ID`
  - `RAG_TOP_K` (например 5)
  - `RAG_MIN_SCORE` (например 0.2–0.35, подобрать эмпирически)

---

## 5) Поток обработки запроса

1. Пользователь пишет вопрос в MAX.
2. Бот выполняет retrieval по `YA_RAG_INDEX_ID`.
3. Если нет релевантных чанков -> шаблон отказа (без генерации «из головы»).
4. Если чанки есть -> формирует `CONTEXT` (с метаданными источников).
5. Вызывает модель YandexGPT с жестким system prompt + context.
6. Возвращает ответ + цитаты источников.
7. Логирует результат для контроля качества.

---

## 6) Минимальный шаблон ответа пользователю

- При наличии данных:
  - Краткий ответ
  - Подробности
  - Источники: `[docA:12] [docB:4]`

- При отсутствии данных:
  - `Недостаточно данных в предоставленных документах.`
  - `Чтобы ответить, в базе должны быть сведения о ...`

---

## 7) Риски и как снизить

- **Риск:** модель всё равно «додумает».  
  **Митигация:** pre-check/post-check + обязательные цитаты + отказ при пустом retrieval.

- **Риск:** нерелевантные чанки при коротких запросах.  
  **Митигация:** query-rewrite (локально), поднятие `top_k`, настройка порога релевантности.

- **Риск:** слишком длинный context.  
  **Митигация:** rerank + ограничение токенов + extractive summary по чанкам.

---

## 8) Практический план внедрения (итеративно)

1. Форкнуть каркас `max-yandexgpt` в ваш внутренний репозиторий.
2. Добавить `retriever` модуль для AI Studio Search Index.
3. Добавить `grounding_policy` (правила отказа/цитирования).
4. Внедрить structured logging для аудита.
5. Прогнать тест-кейсы:
   - вопрос покрыт документом;
   - вопрос частично покрыт;
   - вопрос не покрыт;
   - конфликтующие документы.
6. Добавить smoke-набор регрессионных запросов перед деплоем.

---

## 9) Итог

Оптимальная комбинация:
- MAX-обвязка из `max-yandexgpt`;
- retrieval и работа с индексом из `yandex-ai-studio-sdk`;
- из `yc-ai-tg-demo` взять только организационные паттерны RAG-пайплайна, но исключить Search API интернет-поиск.

Ключевой принцип: **retrieval-first + no-context-no-answer**. Это и обеспечивает «строго по предоставленным документам».
